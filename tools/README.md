# tools/ — 診断・検証スクリプト

本番の自動更新には**関与しない**、手元で実行する調査用スクリプト置き場。
`.github/workflows/` からは呼ばれない。

## 収録スクリプト

| ファイル | 用途 | 終了コードで結論が出る |
|---|---|---|
| `diag_ais.py` | AISstream.io の疎通診断。ホルムズ bbox と全世界 bbox の対照実験 | 0=正常 / 10=bbox・カバレッジ問題 / 20=サービス側 / 30=接続・認証 |
| `diag_ais_coverage.py` | 全世界 bbox で受信し、**地理的に集計してカバレッジの実在を判定** | 0=ホルムズで受信 / 10=中東圏で受信 / 20=中東が完全空白 / 30=接続・認証 |
| `diag_gfw.py` | Global Fishing Watch API がホルムズの通航船を返すかの実現可能性検証 | 0=検出できた / 10=0件 / 20=認証 / 30=パラメータ不正 |
| `diag_vesselapi.py` | VesselAPI の無料枠でホルムズの通航船が取れるかの実現可能性検証 | 0=検出できた / 10=当該海域のカバレッジ無し / 20=API・アカウント側 / 30=接続・認証 |

いずれも**読み取り専用**（ファイルを書かない）。API キーは環境変数から読む。ハードコードしない。

## なぜ残してあるか

2026-09-01 の調査で、AISstream.io に**ペルシャ湾・ホルムズ海峡の受信局カバレッジが存在しない**ことが判明した
（全世界 bbox は60秒で3,467隻、ホルムズ bbox は180秒で0隻。最寄りの受信船まで約1,900km）。
この状態のまま 2026-04-15 から約4.5か月、`vessels_detected: 0` を書き続けていた。

**契約・実装の前にカバレッジを実測する**という手順を踏んでいれば防げた失敗であり、
`diag_ais_coverage.py` の手法（全世界受信 → 地理的集計）は次のデータソース選定で再利用できる。

新しい AIS ソースを検討する際は、**必ず無料枠・トライアルの範囲でホルムズ bbox の実測を行ってから**契約すること。

## AIS データソース選定の結論（2026-09-05 確定・実測は当面断念）

**AIS 実測は当面断念し、「AI 推計のみ・出自を明示して運用」を正式な方針とする。**

VesselAPI の無料枠を採用する方向で `scripts/fetch_ais.py` を実装済みだが（commit `c8f9636`）、
**提供元からの回答（2026-09-04）を受けて有効化を見送った**。規約は許諾されたが、
**通航レーンのカバレッジが薄く、数値が交通量ではなくカバレッジを表してしまう**ため。
有料プランでも解決しない。詳細は「採用は見送った（2026-09-05 決定）」の節を参照。

実装はそのまま残してあり、カバレッジが改善すれば有効化手順だけで切り替わる。
以下は選定の経緯と、再検討時に踏まえるべき制約の記録。

### 満たすべき要件

1. **ホルムズ海峡／ペルシャ湾の実カバレッジ**（地上 AIS だけでは届かない。衛星 AIS またはそれに準ずる補完が要る）
2. **「取得成功かつ0隻」と「取得失敗」をレスポンスから区別できること**
   （AISstream.io は WebSocket ストリーム型のため両者が同じ `0 / 0` になり区別不能だった。
   VesselAPI は不正キー `HTTP 401 / invalid_api_key`、船のいない海域 `HTTP 200 / vessels: []`
   で返ることを実測で確認済み）
3. **日次1回の取得で足りる**（現行 cron は日次。リアルタイム性は要件外）
4. **公開サイトでの表示が利用規約上許されること**（ここが最大の制約）

### ライセンス上の注意（重要）

Datalastic の利用規約は、**生データ・API レスポンスをそのままの形で公開アプリケーションに表示すること**を禁じている。
一方で、**分析・可視化・ダッシュボード等の付加価値プロダクトの作成は認められている**（生データを露出させず、
サービスの代替として機能しない限り）。

当サイトの用途は個船情報ではなく**通航隻数の集計値の表示**であるため、許容範囲に入る可能性が高いが、
**これは条文の解釈であり確定ではない。契約前に提供元へ書面で確認すること**（確度：中）。
同種の条項は他の商用プロバイダにも存在するのが通例のため、候補ごとに同じ確認が要る。

### VesselAPI の制約（ドキュメント記載・2026-09-03 確認）

当時の無償運用の最有力候補であり、採用検討時に洗い出した制約が5つある（記録として残す）。

1. **API キーの有効期限は最長 90 日**（30/60/90 から選択）。無料プラン自体の期限ではなくキーの寿命。
   運用に乗せるなら必ず 90 日を選び、**90日ごとに再発行して GitHub Secret を更新する**必要がある。
   忘れると取得が黙って止まる — 今回の「4.5か月0隻」と同型の事故になるため、
   401/403 を受けたらワークフローを失敗させ、通知が届く状態を保つこと
2. **bbox 検索の time 窓は最大4時間**（`time.to - time.from` ≤ 4h）。
   日次1回で取れるのは「1日の通航量」ではなく**ある時点のスナップショット**であり、
   1日を通して数えることはできない。
   → 実装では `time.from` / `time.to` を**指定せず API 既定の窓を使う**。
   4時間窓に広げてもコールが2.3倍になるだけで移動中の船は5→6隻しか増えなかったため
   （下記「実測結果」）。表示側のカードも「当日の総通航量」ではなくスナップショットとして読むこと
3. **`pagination.limit` は最大50**。輻輳海域ではページングが要り、1スナップショットで複数コールを消費する。
   月間コール数の試算は実測してから行うこと
4. **bbox の総スパン `|dLat| + |dLon|` は 4 度以内**（2026-09-03 に実測で判明。公開ドキュメントに記載なし。
   超えると `HTTP 400 / invalid_parameter` で、**クォータは消費されない**）。
   旧 AISstream 版の BBOX（lat 22-27 / lon 55.5-60.5）はスパン和 10 度で通らなかった。
   同じ範囲を覆うにはタイル分割が必要で、2度×2度のタイルなら 9 タイル＝1回あたり9コール。
   日次でも月270コールとなり**無料枠150を超える**。
   → 実装では監視範囲を**ホルムズ海峡本体の1タイル**（lat 25.8-27.0 / lon 55.6-57.0、
   スパン和 2.6 度）に絞った。`scripts/fetch_ais.py` の `BBOX` と `diag_vesselapi.py` の
   `HORMUZ` は同じ値。**bbox を広げる場合はスパン和 4 度以内を必ず確認すること**
5. **bbox レスポンスに船種フィールドが無い**（`cog` / `heading` / `imo` / `latitude` / `longitude` /
   `mmsi` / `nav_status` / `sog` / `timestamp` / `vessel_name`）。
   現行の breakdown（tanker / cargo / other）はこのエンドポイントだけでは作れない。
   船種は MMSI ごとの別エンドポイントになり、隻数ぶんのコールを消費して無料枠が破綻する見込み

**衛星応答は月次クォータを消費せず、別枠の衛星クレジットで支払う**とドキュメントに明記されている。
無料プランに衛星クレジットが付くとは書かれていないため、無料枠で取れるのは地上 AIS のみと思われる。
ただし**ホルムズ海峡では実際にデータが返ることを実測で確認済み**（下記）。
`X-Data-Source` ヘッダは返ってこないため、地上／衛星の別は判別できない。

### 実測結果（2026-09-03・`diag_vesselapi.py`）

**bbox 内でデータが返ることは確認できた（AISstream.io の完全な空白とは異なる）。**
ただし後日、**捕捉のほとんどが通航レーンの西側に偏っている**ことが提供元の実測で判明した。
以下の隻数は「海峡の交通量」ではなく**提供元のカバレッジ範囲**を表している。

| 時間窓 | 消費コール | ユニーク隻数 | 移動中（sog≧1kt） | 停泊・漂泊 | 月間試算 |
|---|---|---|---|---|---|
| API既定 | 3 | 21 | **5** | 16 | **90（無料枠内）** |
| 4時間 | 7 | 34 | 6 | 28 | 210（超過） |

**時間窓を4時間に広げてもコールが2.3倍になるだけで、移動中の船は5→6隻しか増えない。**
増分13隻はすべて錨泊船だった。4時間窓にコストを払う理由がない。

その他、実測で分かったこと:

- **返るのは「船のリスト」ではなく「位置報告のリスト」**。145レコードでユニークは21隻
  （1隻あたり平均7件）。`pagination.limit=50` は「50隻」ではなく「50メッセージ」。
  **取得側で MMSI による重複排除が必須**
- **失敗と0隻は構造的に区別できる**。不正キーは `HTTP 401 / invalid_api_key`、
  船のいない海域（南太平洋）は `HTTP 200 / vessels: []` で返る。
  → 依頼2の論点3で **3-C（三値化）が縮退せずに成立する**
- **クォータは成功リクエストのみ消費**（1コール=1）。401 と 400 は消費されない
- **返るフィールドは船ごとに可変**（`cog` / `heading` が欠ける船がある）。取得側の防御が要る
- 未文書フィールド `location` は GeoJSON Point（`[lon, lat]`）。緯度経度と重複し使い道なし
- 錨泊船が多いのは bbox 内に錨泊地が入っているため。
  **当初これをホル・ファッカン沖と推定したが誤りで、実際はケシュム島・バンダルアッバス沖
  （イラン側）だった**（2026-09-04 に提供元の実測で判明。下記）。
  「危機時の錨泊待機の急増は封鎖の先行シグナルとして価値がある」という当初の見立ては、
  bbox の捕捉が通航レーンの西側に偏っていることを踏まえておらず、成立しない

### 採用は見送った（2026-09-05 決定）

**2026-09-03 に「採用構成」としてまとめ実装まで進めたが、提供元からの回答を受けて有効化を見送った。**

規約上は問題なかった（無料プランのまま集計値の公開が許可され、出典表示も不要、
許諾は URL でなく用途に紐づく）。**見送りの理由はデータの妥当性のほうにある。**

提供元 Bence が同一 bbox を4時間窓で実測した結果:

| 区分 | 隻数 |
|---|---|
| bbox 全体 | 57 |
| **うちケシュム島・バンダルアッバス沖の狭い海域** | **46** |
| **東経 56.1 度以東（実際の通航レーン）** | **6**（うち4隻は錨泊） |
| bbox 全体で 1kt 超で移動中 | 10 |

**この数値は「海峡の交通量」ではなく提供元のカバレッジ範囲を表すものになる。**
日次の数値は船舶の動きと同じくらいカバレッジの変動で動き、読者はその低下を
「出来事」として受け取る。提供元自身が「この数値を交通量の指標として公表することは勧めない」
と明言し、**有料プランでもクレジットパックでも解決しない**（衛星測位は船単位のリクエストで
エリアを埋められない）ことも明示された。当該海域のカバレッジ改善は作業中だが時期は未定。

### 確定した方針（2026-09-05）

**AIS 実測は当面断念し、「AI 推計のみ・出自を明示して運用」を正式な方針とする。**
誤った通航量を出す誤報コストは、推計値を出す誤りより桁違いに重い。

- **`.github/workflows/update_ais.yml` は `if: false` のまま維持する**（有効化しない）
- 実装（下記）はそのまま残す。カバレッジが改善したときに有効化できる状態を保つ
- **VesselAPI のアカウントとキーは維持する**（無料・維持コストゼロ）。キーは **2026-12-02 失効**。
  9日前（11/23頃）と失効時にメール通知が来る。使わないなら更新しなくてよい
- **四半期ごとに `diag_vesselapi.py --count` を回し、カバレッジの変化を測る**。
  特に **56.1E 以東の移動中隻数**を見る。改善していれば採用を再検討する
- カバレッジが実用水準に達した場合、または広告を導入する場合は提供元に再連絡する
  （本人から「計画が変わったら、データをより広く使いたくなったら連絡を」と申し出がある）

回答の全文・許諾条件・判断の経緯は `vesselapi-inquiry.md` を参照。

### 実装状況（2026-09-03・commit `c8f9636`）

実測と推計の分離、および VesselAPI への移行は**実装・push 済み**。

| 対象 | 状態 |
|---|---|
| `scripts/fetch_ais.py` | VesselAPI(REST) 版に全面書き換え済み。**実測の唯一の書き手** |
| `data/ais-snapshot.json` | 実測専用にリセット済み（現在は `fetch_ok: false` の未取得状態） |
| `data/ais-estimate.json` | 新規。推計専用（`scripts/fetch_manual.py` が書く） |
| `index.html` の `loadAIS()` | 2ファイル対応。実測を優先し、条件を満たさない場合のみ推計へフォールバック |
| `.github/workflows/update_ais.yml` | **無効（`if: false`）のまま維持**。規約は許諾済みだが、カバレッジ不足のため有効化しない |

**実測0隻の扱い**: ホルムズが0隻だったときに限り対照海域（シンガポール海峡）を
1コール叩き、そこに船がいれば真のゼロとして表示、対照も0なら API 障害として推計へ退避する。
通常時は追加コールを消費しないため、月90コールは変わらない。

**未検証**: VesselAPI への実通信は未実施（ローカルに API キーが無いため）。
HTTP まわりは `diag_vesselapi.py` で実証済みの仕様に合わせた実装であり、実応答での確認は未了。
有効化時に必ず `workflow_dispatch` で1回試すこと。

**有効化手順（当面実行しない。カバレッジが改善した場合にのみ使う）**:
1. GitHub Secret に `VESSELAPI_API_KEY` を登録（キーの有効期限は**90日を選ぶ**）
2. `.github/workflows/update_ais.yml` の `schedule` のコメントを外し、`jobs.fetch-ais.if: false` を削除
3. `workflow_dispatch` で1回試し、`data/ais-snapshot.json` が実測値で更新されることを確認
4. GitHub Pages で表示が「実測（AIS受信）」に切り替わることを確認

**現在の表示**: 実測が入らないため、`loadAIS()` は常に推計側にフォールバックし、
出自バッジは「AI推計」で固定される。3-C の三値化構造は入っているので、
カバレッジ改善時は上記の有効化手順だけで実測表示に切り替わる。
